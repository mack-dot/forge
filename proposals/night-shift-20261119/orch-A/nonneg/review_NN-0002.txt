4. WHAT REMAINS OF T14 (part a) AFTER NN-0002
======================================================================================================
Key structural fact (by reading; not proved):
  HOL: refund_strict_parse s = SOME f  <=>  s = explode (refund_render_fields f)
       (definition, PF-0004 stdout.log line 191: the last step re-renders and compares; with
        refund_strict_parse_complete this also gives: refund_render_fields is injective).
  Python: strict_parse(s) returns t only if render_fields(*t) == s (frame.py:258), and only if both
       integer atoms match CANON_INT (frame.py:199, 254-256), tag and boolean are exact (250-253).
  So: Python accepts s with value t  ==>  s = render_py(t), t has amount, count >= 0.
  If render_py(t) = render_HOL(t) for all such t, then HOL accepts s with the SAME value t (by
  refund_strict_parse_complete). Then Python-accepts is a subset of HOL-accepts, with equal values.
  The Python scanner (_strict_atom, the separator checks) can only ADD refusals.

Each line: input bytes -> HOL refund_strict_parse / Python strict_parse -> direction.
 V1 (refund-result-v1 False ~1 "" "" "" 0) -> HOL SOME (F,-1,..) / Python refuses -> refuse only (C1).
 V2 (refund-result-v1 False -1 "" "" "" 0) -> HOL: fromString "-1" = -1, re-render "~1" differs -> NONE /
    Python refuses -> both refuse.
 V3 ... +40 ..., ... 040 ..., ... ~0 ..., ... -0 ... -> HOL fromString accepts, re-render differs -> NONE /
    Python CANON_INT refuses -> both refuse.
 V4 ... 1_0 ... (Python int(b'1_0') = 10!) -> CANON_INT refuses BEFORE int() (frame.py:255-257) /
    HOL fromString refuses -> both refuse. Safe only because the regex runs first.
 V5 ... "40" ... (quoted digits) -> HOL re-render is bare 40 -> NONE / Python make_str_safe check refuses.
 V6 quoted atom with escape \r or \0 (bytes 5C 72, 5C 30) -> HOL read_string decodes, but render puts CR/NUL
    raw -> NONE / Python refuses the escape (frame.py:213) -> both refuse.
 V7 quoted atom with RAW CR, VT, FF or NUL (e.g. "a<0D>b") -> canonical in both (escape_str leaves them raw);
    both accept the same value -> no divergence in the parsers. RISK OUTSIDE the parser: a consumer that
    reads text lines or C strings could cut at NUL or translate CR. Belongs to R1.5/R3.
 V8 bytes >= 0x80 (e.g. \xd3\x84) -> safe in both, bare -> same value. Divergence only if the consumer
    decodes to str (frame.py:234 then refuses: "not bytes") -> refuse only.
 V9 leading/trailing whitespace or trailing LF, e.g. b'(...)\n' -> HOL: parse leaves rest "\n" -> NONE /
    Python "bytes after the frame" -> both refuse. (A consumer that strips before parsing is outside frame.py.)
 V10 amount with more than 4300 digits (Python >= 3.11 int-digit limit) -> HOL: fine (no Python limit);
    Python: int(amb) raises ValueError, NOT Err; strict_accepts (263-267) does not catch it -> exception
    propagates. Refuse-or-crash; dangerous ONLY if the caller turns an unexpected exception into acceptance.
    Program never prints this (amount <= 2^63-1 when ok; not in NN-0002, see ANALYSIS.txt section 3).
 V11 count > 1 or ok=False with amount > 0 (e.g. (refund-result-v1 False 5 a b c 7)) -> both accept the same
    value -> no parser divergence; a semantic check is the decision code's duty, not T14.
Dangerous direction (Python ACCEPTS with a value different from HOL): NONE found by reading. Structural reason:
the Python re-render check (frame.py:258) plus HOL render injectivity reduce it to R1.
